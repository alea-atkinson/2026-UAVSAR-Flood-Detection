# Real-Tile Q.20 Verification: All 32 First-Layer Output Channels

Date: July 23, 2026

This report extends the real-tile VHDL verification from the original
kernel0/kernel2 subset
(`hardware/vhdl_conv3x3/reports/real_tile_first_layer_vhdl_verification_summary.md`,
Q.16) and the Q.20 precision/synthesis follow-ons
(`hardware/vhdl_conv3x3/reports/real_tile_fixed_point_precision_sensitivity_summary.md`,
`hardware/vhdl_conv3x3/reports/real_tile_q16_vs_q20_synthesis_comparison_summary.md`)
to **all 32 output channels** of the first Conv-BN-ReLU stage, at Q.20,
on the SAME real UAVSAR-tile-derived patch.

## Claim boundary (read this first)

- **This is simulation-only (GHDL) verification.** No synthesis was rerun
  for this task. No board testing, no measured speedup, no measured
  power.
- **This is NOT full FPGA U-Net, NOT board deployment, and NOT
  full-image streaming.** It verifies the first Conv-BN-ReLU stage's 32
  output channels on ONE real 6x6x3 UAVSAR sub-block (16 valid 3x3
  windows per channel) -- the same real patch already used for the
  kernel0/kernel2 subset, not a full 256x256 tile pass.
- **This is 32 INDEPENDENT single-kernel pipelines run together in one
  simulation, not the separate, complete 32-output resource-shared
  design** (`stream_conv3x3_3chan_32out_bn_relu_time_mux`). That design
  is untouched by this task; extending real-tile input to it remains a
  distinct, larger undertaking (unchanged from the original
  kernel0/kernel2 report's own assessment).
- **No existing committed VHDL file was modified.** Every new entity,
  package, testbench, and run script is a new, clearly-named file. The
  only Python script changed was the vector generator's `--kernel-id`
  CLI restriction (relaxed from `choices=[0, 2]` to `0-31`); the
  generation logic itself was already fully general per-kernel and this
  change was verified to reproduce byte-identical output for kernels 0
  and 2 before being trusted for the other 30.
- **No hardware architecture was invented.** All 32 per-kernel DUTs are
  structurally IDENTICAL to the already-verified
  `stream_conv3x3_3chan_kernel0_bn_relu_real_tile_q20.vhd` -- same
  `stream_conv3x3_3chan_cell` sub-component, same two-stage registered
  Q.20 BatchNorm-fold + ReLU pipeline -- generated by mechanical template
  substitution (kernel index only), not redesigned.
- **No GHDL `.o` files or testbench binaries were added or committed** --
  all such artifacts are covered by `hardware/vhdl_conv3x3/.gitignore`
  (the new combined testbench's binary name was added to that file).

## What was done

1. **Inspected** the existing real-tile Q.20 files per the task's
   instruction: the generator script, `kernel0_q20`/`kernel2_q20` vector
   directories, the 2-kernel combined testbench, and its run script.
2. **Relaxed** `scripts/generate_real_tile_bn_relu_fixed_point_vectors.py`'s
   `--kernel-id` argument from `choices=[0, 2]` to the full `0-31` range
   -- the underlying BatchNorm-folding/quantization/convolution logic
   already indexed the checkpoint's tensors generically per kernel; only
   the CLI validation was narrowed. Verified this change reproduces
   BYTE-IDENTICAL output for kernel 0 (md5sum match, package + JSON + CSV)
   before trusting it for the other 30 kernels.
3. **Generated Q.20 golden-vector artifacts for kernels 0 through 31**
   by calling the (now-relaxed) generator 32 times with `--frac-bits 20
   --variant-suffix _q20` -- reusing kernels 0 and 2's already-existing
   output, generating 30 new ones.
4. **Generated 30 new per-kernel VHDL entity files**
   (`stream_conv3x3_3chan_kernel{K}_bn_relu_real_tile_q20.vhd` for K in
   {1, 3-31}) via a new templating script
   (`scripts/generate_all32_kernels_real_tile_q20_vhdl.py`), by
   mechanically substituting the kernel index throughout the
   already-verified kernel-0 Q.20 entity's text -- kernels 0 and 2's
   existing entity files were left untouched.
5. **Generated ONE combined all-32-kernel testbench**
   (`tb_stream_conv3x3_3chan_all32_kernels_real_tile_bn_relu_q20.vhd`),
   satisfying the task's first offered option ("one all-32-kernel Q.20
   testbench, if practical") -- practical here because every DUT is
   structurally identical and the same real pixel stream drives all 32
   in parallel within one simulation.
6. **Ran GHDL** against the new testbench.
7. **This report.**

## Limitations

- **One real tile, one 6x6 sub-block location.** A different tile or
  offset was not tried for all 32 kernels (the precision-sensitivity
  report's Q.16-vs-Q.20 comparison was likewise limited to this same
  tile/offset).
- **Valid (no-padding) convolution only** -- matches every VHDL prototype
  in this repo; padding is not implemented anywhere in VHDL.
- **Simulation-only (GHDL).** No synthesis was rerun for all 32 kernels
  in this task (the kernel0/kernel2 Q.16-vs-Q.20 synthesis comparison
  already showed Q.20's per-kernel resource/timing cost over Q.16 is
  negligible; synthesizing all 32 kernels together, e.g. in a true
  resource-shared design, was not attempted here).
- **32 independent single-kernel pipelines, not a resource-shared
  design.** This report says nothing about the resource cost of running
  all 32 kernels SIMULTANEOUSLY in one FPGA (that would require either
  32x the per-kernel resource footprint if fully parallel, or a
  time-multiplexed/resource-shared architecture like the existing
  `stream_conv3x3_3chan_32out_bn_relu_time_mux`, which remains a
  separate, unmodified design not extended to real-tile input here).
- **No board testing, no measured speedup, no measured board power.**
- **This does not retrain, fine-tune, or otherwise modify the
  checkpoint.**
