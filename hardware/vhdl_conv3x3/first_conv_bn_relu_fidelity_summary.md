# First Conv-BN-ReLU Folding Fidelity Summary

Date: July 7, 2026

Generated by: `scripts/analyze_first_conv_bn_relu_fidelity.py`

This is an **analysis document**, not a new RTL task. No VHDL or hardware
files were created or modified to produce this report.

## Purpose

`scripts/analyze_first_layer_quantization_fidelity.py` (see
`hardware/vhdl_conv3x3/first_layer_quantization_fidelity_summary.md`)
compared raw PyTorch float `Conv2d` output against an INT8/fixed-point-style
raw `Conv2d` approximation -- no BatchNorm, no activation. That study's own
"Recommended next step" was to fold BatchNorm into the Conv2d weights/bias
and measure the fidelity of the **folded, quantized Conv-BN-ReLU stage**
against the **true PyTorch `Conv2d -> BatchNorm -> ReLU`** computation. This
document is that next step.

**This is still Python numerical fidelity only, for the first Conv-BN-ReLU
stage only:**

1. **"VHDL matches Python fixed-point"** -- NOT applicable here. No VHDL
   module in this repo implements BatchNorm, bias, or ReLU. Every VHDL
   prototype in `hardware/vhdl_conv3x3/` still only computes the raw
   valid-convolution datapath with `bias_int32 = 0`.
2. **"Fixed-point (folded) approximates PyTorch float (Conv-BN-ReLU)"** --
   THIS is what this script measures.

## Method

1. Load `models/alea_tuned_filtered_strict_fp2_focaldice_adamw_20epochs_best.pt`
   and extract:
   - `enc1.block.0.weight` (Conv2d, `[32, 3, 3, 3]`, no direct bias)
   - `enc1.block.1.weight`, `.bias`, `.running_mean`, `.running_var`
     (BatchNorm2d(32), affine, eval-mode running statistics)
2. Fold BatchNorm into the Conv2d weights and bias (formula below).
3. Quantize the **folded** weights to INT8 (symmetric, per-output-channel).
4. Quantize each input patch to INT8 (symmetric, per-patch), same
   convention as the earlier raw-Conv2d study.
5. Compute the INT32 valid-convolution accumulation, rescale, add the
   folded bias (in float, not quantized), apply ReLU.
6. Compare against the true PyTorch `Conv2d(padding=1) -> BatchNorm ->
   ReLU` output, restricted to the valid interior region (see below).
7. Before trusting the quantized comparison, run a **folding sanity check**
   in float only (no quantization) to confirm the folding formula and the
   valid-interior cropping logic are correct.

## Valid-interior comparison scope (explicit)

The real PyTorch `Conv2d` uses `padding=1`, so its output has the same
spatial size as its input. Every VHDL prototype in this repo computes
**valid (no-padding) 3x3 windows only** -- padding is **not implemented**
in any VHDL module here. To make an apples-to-apples comparison:

1. The true PyTorch `Conv2d(padding=1) -> BatchNorm -> ReLU` is run on the
   **full** patch (5x5 or 16x16), exactly as the real model would compute
   it.
2. Only the **valid interior region** is kept -- the outermost 1-pixel
   border is cropped away. For a 5x5 input this leaves the central 3x3
   region; for a 16x16 input this leaves the central 14x14 region. This
   cropped region's receptive field never touches the padding, so it is
   mathematically identical to a true valid (no-pad) convolution over the
   same patch.
3. That cropped region is compared against the valid (no-pad) folded/
   quantized computation.

**This does not evaluate padded border behavior, and does not imply that
VHDL implements padding.** Only the interior, padding-independent positions
are compared.

## BatchNorm folding formula

```
scale_bn[oc]  = gamma[oc] / sqrt(running_var[oc] + eps)
w_folded[oc]  = w[oc] * scale_bn[oc]
b_folded[oc]  = beta[oc] - running_mean[oc] * scale_bn[oc]
```

`eps = 1e-5` -- the `torch.nn.BatchNorm2d` default. Verified (not assumed):
`train_unet_baseline_tuned.py`'s `DoubleConv` module instantiates
`nn.BatchNorm2d(out_channels)` with no `eps` override, so the PyTorch
default applies.

Measured folding parameters:

| Parameter | Range |
|---|---|
| `scale_bn` | 0.725900 to 4.089005 |
| `b_folded` | -0.044762 to 0.040213 |

The `scale_bn` range (0.73x to 4.09x) is notably wider than gamma's own
range (0.9871 to 1.0099, per the earlier study's BatchNorm inspection) --
this is expected, since `scale_bn` also divides by `sqrt(running_var +
eps)`, and `running_var` itself ranges from 0.061 to 1.903 across the 32
channels (also from the earlier study), so channels with small running
variance get proportionally amplified folded weights.

## Folding sanity check (float only, before quantization)

Confirms: `valid_conv(x, w_folded) + b_folded`, ReLU'd, **exactly equals**
the center-cropped `[Conv2d(x, w, padding=1) -> BatchNorm -> ReLU]`, up to
floating-point rounding.

| Patch | Max diff | Mean diff |
|---|---:|---:|
| `toy_5x5_synthetic` | 7.693e-06 | 7.954e-07 |
| `real_tile_16_42.tif` | 1.133e-06 | 4.762e-08 |
| `real_tile_16_43.tif` | 8.841e-07 | 4.649e-08 |
| **Overall** | **7.693e-06** | **2.965e-07** (mean of per-patch means) |

**PASSED.** All differences are at float32 rounding-error scale (~1e-6),
confirming both the folding formula and the valid-interior cropping logic
are correct before any quantization is introduced.

## Quantization scheme

- **Folded weights**: symmetric per-output-channel INT8,
  `scale_w_folded[oc] = max(|w_folded[oc]|)/127`, same clipping convention
  as the earlier study, applied to the **folded** weights instead of the
  raw weights. Measured range: **0.00106709 to 0.00575681** across the 32
  kernels -- a much wider range than the raw-weight study's 0.00136063 to
  0.00156223, directly reflecting the `scale_bn` amplification per channel.
- **Activations**: identical per-patch symmetric scheme to the earlier
  study (`scale_x = max(|x_patch|)/127`), unchanged.
- **Folded bias**: added in float (not quantized) after rescaling the
  INT32 accumulation, matching the task's explicit instruction.
- **ReLU**: applied last, identically to both the PyTorch reference and the
  folded/quantized approximation.

## Interpretation

- BatchNorm folding is confirmed **exact in float** (folding sanity check,
  ~1e-6 differences, floating-point precision only) -- the folding formula
  and valid-interior cropping logic are correct.
- Once INT8 quantization of the **folded** weights and activations is
  introduced, the Conv-BN-ReLU stage's fidelity to the true PyTorch
  computation is **similar in relative terms** to the raw-Conv2d-only study
  (~0.82% mean relative error here vs. ~0.83% previously; correlation and
  cosine similarity both remain above 0.9999), but **somewhat worse in
  absolute terms** (MAE 0.005029 vs. 0.004293, about +17%; max absolute
  error 0.655282 vs. 0.215443, about 3x higher).
- This absolute-error increase is plausibly explained by the **much wider
  `scale_w_folded` range** (0.00107 to 0.00576, a 5.4x spread) compared to
  the raw-weight study's narrow range (0.00136 to 0.00156, a 1.15x spread).
  BatchNorm folding amplifies some channels' weights by up to ~4.09x
  (`scale_bn`), which coarsens their INT8 quantization step size
  proportionally, and the two kernels with the largest folded-weight scale
  (kernels 2 and 11) are exactly the two kernels with the largest observed
  error in this study.
- This is evidence that folding BatchNorm before INT8 quantization
  introduces a **real, measurable** trade-off: it is necessary for a
  hardware datapath to produce a realistic (BatchNorm-applied,
  ReLU-activated) approximation at all, but per-channel quantization
  granularity becomes less uniform across the 32 output channels than it
  was for the raw (unfolded) weights.

## Limitations

- **Python analysis only.** No VHDL was written, run, or modified.
- **Valid interior positions only.** Padded border behavior is not
  evaluated -- only the interior region whose receptive field never
  touches the `padding=1` border was compared.
- **No VHDL BatchNorm/bias/ReLU implementation yet.** Every VHDL prototype
  in this repo still computes `bias_int32 = 0`, no BatchNorm, no
  activation -- this document does not claim otherwise.
- **No full DoubleConv block.** Only the first Conv-BN-ReLU
  (`enc1.block.0` -> `enc1.block.1` -> ReLU) was analyzed; the second
  Conv2d in `enc1.block` (`enc1.block.3` / `enc1.block.4`) was not
  analyzed.
- **No full U-Net.** Only the first encoder stage's first half is covered.
- **No segmentation metrics.** No Dice, recall, IoU, or any other
  segmentation-level evaluation was performed, with or without
  quantization.
- **No board testing.** All results are Python (NumPy/PyTorch) computation
  only.
- **No measured speedup or measured board power.** No hardware timing or
  power measurement of any kind is claimed here.
- **Small, non-exhaustive sample.** 2 real UAVSAR tiles (16x16 center crop
  each) plus 1 synthetic toy patch -- consistent with the earlier study's
  "small but meaningful" sampling approach, not a comprehensive
  dataset-wide study.

## Recommended next step

Extend this same fold-and-quantize methodology to the **second** Conv2d in
`enc1.block` (`enc1.block.3` weight, `enc1.block.4` BatchNorm), which takes
32 input channels instead of 3 and would complete the full first
`DoubleConv` block's fidelity picture (`Conv-BN-ReLU -> Conv-BN-ReLU`).
That would be the natural next increment before considering any end-to-end
quantized-model accuracy evaluation, and would also clarify whether the
per-channel quantization-granularity effect observed here compounds across
two folded-and-quantized stages.
