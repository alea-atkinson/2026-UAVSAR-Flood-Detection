# First-Layer Quantization Fidelity Summary

Date: July 6, 2026 (updated: split-file and relative-error aggregation fixes)

Generated by: `scripts/analyze_first_layer_quantization_fidelity.py`

This is an **analysis document**, not a new RTL task. No hardware files
were modified to produce this report.

> **Update note**: this revision fixes two issues found in the initial
> version: (1) the real UAVSAR samples now come from the split that
> actually matches the checkpoint under test (see "Real UAVSAR data" below),
> and (2) the overall and per-channel relative-error aggregation methods
> were corrected so the toy patch's much larger magnitude no longer
> silently excludes real-tile samples from the "safe" relative-error
> subset (see "Error metrics" below). All numbers in this document reflect

## Purpose

Every VHDL prototype in `hardware/vhdl_conv3x3/` has already established
that **the hardware computes exactly the INT32 values a Python
golden-vector script predicts** for the first U-Net convolution layer
(`enc1.block.0.weight`), verified bit-for-bit in GHDL across the 1-output,
4-output, 8-output, DSP-aware, time-multiplexed, and streaming
time-multiplexed prototypes. That is a **hardware-datapath correctness**
claim: given the same INT8 weights and INT8 inputs, VHDL and Python agree.

It says nothing about a separate, equally important question:

> **How close is the INT8/fixed-point-style first-layer computation to the
> ORIGINAL PyTorch floating-point first-layer computation?**

This document answers that second question. It measures the numerical gap
introduced by quantizing the real trained weights (and, for real image
patches, the activations) to INT8, relative to running the same patch
through the unquantized `float32` Conv2d. This connects the
bit-true hardware verification work to model-side numerical fidelity,
strengthening the overall FPGA feasibility story.

**These two claims are kept strictly separate in this document and its
underlying script:**

1. **"VHDL matches Python fixed-point"** -- already established elsewhere
   in this repo (GHDL testbenches). Not re-verified here.
2. **"Fixed-point approximates PyTorch float"** -- measured here, for the
   first time, using real trained weights and both real and synthetic
   input patches.

## Method

- Load `models/alea_tuned_filtered_strict_fp2_focaldice_adamw_20epochs_best.pt`
  and extract `enc1.block.0.weight`, shape `[32, 3, 3, 3]` (all 32 output
  channels of the first Conv2d layer).
- Quantize every kernel's weights to INT8 using the **same symmetric
  per-tensor scheme** already established in
  `scripts/export_first_layer_multi_kernel_vhdl_vectors.py`:
  `scale_w[oc] = max(|w_float[oc]|) / 127`, `w_int8[oc] = round(w_float[oc]
  / scale_w[oc])` clipped to `[-127, 127]`.
- For each tested patch: compute (a) the **raw floating-point** valid 3x3
  convolution (no bias, no BatchNorm, no activation -- matching the exact
  scope of every VHDL prototype) for all 32 kernels, and (b) the **INT8
  quantized** valid convolution (INT32 accumulation, same arithmetic
  convention as the VHDL cells), rescaled back to approximate float units by
  multiplying by `scale_w[oc] * scale_x`.
- Compare (a) and (b) with several error metrics, both overall and
  per-kernel.
- **Sanity cross-check**: before trusting any of the above, the script
  reruns kernel 0 on the exact canonical toy patch already used by every
  VHDL testbench (`scale_x = 1.0`, no activation requantization) and
  confirms the result is **exactly 11287** at the top-left position -- the
  same value already verified bit-for-bit in GHDL. This confirms the
  script's INT8 arithmetic is consistent with the hardware-verified path
  before using it to measure float-vs-fixed-point error. **This still
  passes after both fixes below** (verified by rerunning the script).

## Real UAVSAR data vs. toy/synthetic data

**Both were used, clearly labeled.**

- **Real UAVSAR data**: 2 tiles were loaded from the **IEEE PNG-filtered
  strict** held-out `fp2` test split
  (`csv_splits/flood_splits_ieee_png_filtered_standard_strict_train_val/strict_no_overlap/heldout_fp2_test.csv`).
  This is the split that actually corresponds to this checkpoint: the
  checkpoint filename
  (`alea_tuned_filtered_strict_fp2_focaldice_adamw_20epochs_best.pt`)
  indicates the "filtered_strict" / IEEE PNG-filtered dataset variant, held
  out on flight path `fp2`. **The initial version of this study incorrectly
  used the broader `flood_splits_standard_strict_train_val` split**, which
  is a different (larger, unfiltered) dataset variant and does not
  correspond to this checkpoint's actual training data -- that has been
  corrected here. Tiles `tile_16_42.tif` and `tile_16_43.tif` (the first
  two loadable tiles from the corrected split) were read with `rasterio`
  and normalized with the **exact same per-tile percentile-clip +
  zero-mean/unit-variance normalization** used by
  `FloodTileDataset._normalize_per_tile` in `train_unet_baseline_tuned.py`,
  so the input distribution matches what the model actually saw during
  training/evaluation. A 16x16 center crop was taken from each tile (196
  valid 3x3 output positions per tile) to keep this analysis small and
  fast -- not the full 256x256 tile.
- **Synthetic/toy data**: the canonical 5x5x3 toy patch used throughout
  every VHDL testbench in this repo (channel 0 = 1..25 row-major, channel 1
  = 2x channel 0, channel 2 = -1x channel 0), included primarily as the
  cross-check described above, and secondarily as one more data point in
  the error-metric tables.

Real UAVSAR data was straightforward to load (Option A from the task
instructions) -- no synthetic-only fallback was needed.

## Quantization scheme

- **Weights**: symmetric per-tensor INT8, per-kernel scale
  (`scale_w[oc] = max(|w_float[oc]|)/127`) -- identical formula to the
  existing hardware export scripts. Measured `scale_w` range across all 32
  kernels: **0.00136063 to 0.00156223** (unchanged by either fix -- weight
  quantization does not depend on which input patches are tested).
- **Activations**: the existing hardware scripts only ever used an already
  integer-valued toy input with `scale_x = 1.0` (no quantization step was
  needed). Real UAVSAR patches are floating-point after normalization, so
  this script introduces one new, clearly-labeled choice: a simple
  per-patch symmetric scheme, `scale_x = max(|x_float_patch|)/127`, applied
  independently to each analyzed patch (toy and real alike, for a
  consistent comparison). **This is not an existing hardware convention --
  no VHDL in this repo yet quantizes real-image input activations.** The
  toy patch's error-metric entry therefore uses a *different* INT8
  representation than the hardware-verified cross-check (which uses the
  original `scale_x = 1.0` convention); this is intentional and documented
  in the script, not an inconsistency to be resolved.
- Bias: 0 for all kernels (Conv2d has no direct bias; BatchNorm is not
  applied or folded -- see BatchNorm section below).

## Error metrics

This section is split into two clearly separate parts, as required: (1)
**absolute-error metrics** computed across all output values directly, and
(2) a **relative-error metric** that must be aggregated differently because
naive division blows up near zero-crossings -- see the aggregation-fix
explanation below.

### 1. Overall absolute-error metrics (across all outputs, all patches, all 32 kernels)

12,832 total output values (toy patch's 9 positions + 2 real tiles' 196
positions each, all x 32 kernels):

| Metric | Value |
|---|---:|
| Mean absolute error (MAE) | 0.004293 |
| Max absolute error | 0.215443 |
| P50 absolute error | 0.002515 |
| P90 absolute error | 0.006501 |
| P99 absolute error | 0.057249 |
| Pearson correlation | 0.999980 |
| Cosine similarity | 0.999980 |

### 2. Relative-error metric: aggregated from per-patch safe subsets (fixed)

**Why relative error needs special handling, and what was wrong before:**
relative error (`|error| / |float_value|`) blows up near zero-crossings, so
it is only computed on a "safe" subset where `|float_value|` exceeds 5% of
that same array's own max magnitude. The **initial version of this script**
computed that 5%-of-max threshold once, globally, on all patches
concatenated together -- and because the toy patch's raw output magnitudes
are far larger than the real (normalized) UAVSAR tiles' output magnitudes,
the global threshold was effectively set by the toy patch alone, which
silently excluded nearly all real-tile samples from the "safe" subset (the
original run reported only 238 total safe samples -- exactly the toy
patch's own count, even though the two real tiles individually had
thousands of samples that individually looked "safe").

**Fix**: each patch's safe relative-error values are now computed using
**that patch's own threshold** (as they always were for the *per-patch*
rows), and the overall/per-channel aggregates are formed by **pooling those
already-computed per-patch safe values together and averaging the pooled
set** -- never by re-deriving a single global threshold from mixed-scale
data. The toy patch's larger magnitude no longer sets the threshold for the
real UAVSAR patches.

| Aggregate | Mean relative error | Safe samples (n) | Source patches pooled |
|---|---:|---:|---|
| **Overall (corrected)** | **0.008305** (0.83%) | **10,586** | 3 (toy + 2 real tiles) |

Per-patch breakdown of what was pooled into the overall aggregate (full
detail in
`hardware/vhdl_conv3x3/test_vectors/quantization_fidelity/first_layer_quantization_error_summary.csv`):

| Patch | Source | Mean relative error | Safe samples (n) | Total samples |
|---|---|---:|---:|---:|
| `toy_5x5_synthetic` | synthetic toy | 0.009042 | 238 | 288 (32 kernels x 9) |
| `real_tile_16_42.tif` | real UAVSAR (fp2 test, filtered strict) | 0.008663 | 5224 | 6272 (32 kernels x 196) |
| `real_tile_16_43.tif` | real UAVSAR (fp2 test, filtered strict) | 0.007906 | 5124 | 6272 (32 kernels x 196) |

The real tiles now correctly contribute the large majority (10,348 of
10,586, or 97.8%) of the safe samples in the overall aggregate, as expected
given they have far more output positions than the 9-position toy patch --
confirming the aggregation bug is fixed.

### Per-patch absolute-error breakdown

| Patch | Source | MAE | Max abs error | Correlation | Cosine similarity |
|---|---|---:|---:|---:|---:|
| `toy_5x5_synthetic` | synthetic toy | 0.063357 | 0.215443 | 0.999980 | 0.999980 |
| `real_tile_16_42.tif` | real UAVSAR (fp2 test, filtered strict) | 0.002924 | 0.016664 | 0.999977 | 0.999978 |
| `real_tile_16_43.tif` | real UAVSAR (fp2 test, filtered strict) | 0.002948 | 0.013895 | 0.999979 | 0.999979 |

The toy patch shows a visibly higher absolute error than the real tiles.
This is expected and explained by scale, not by the real data being
"easier": the toy patch's raw values range up to 50 in magnitude (large
integers), while the normalized real UAVSAR patches are roughly zero-mean,
unit-variance floats (much smaller absolute magnitude). Since MAE and max
absolute error are **absolute**, not relative, quantities, they naturally
scale with the input's own magnitude. The **relative** error metric (~0.8%
mean, correctly pooled from each patch's own safe subset) and the very high
correlation/cosine similarity (>0.9999 for every patch) are the more
appropriate metrics for judging fidelity across inputs of very different
scale, and both are consistently strong across all three patches.

## Per-channel summary

Full detail (32 rows) in
`hardware/vhdl_conv3x3/test_vectors/quantization_fidelity/first_layer_quantization_per_channel_metrics.csv`.
The per-channel relative-error aggregation uses the same fix described
above: for each kernel, each patch's own safe subset (using that patch's
own threshold, restricted to that kernel's data) is computed first, then
pooled across patches. As a result, `n_relative_error_samples` per kernel
is now **~340-380 out of 401 total samples** (up from a handful when the
bug was present), confirming real-tile samples are now correctly included
per kernel as well, not just in the overall aggregate.

All 32 kernels show correlation and cosine similarity above **0.999**, with
one kernel (26) noticeably lower than the rest (0.9994 vs. >0.9998 for most
others) -- worth a closer look if this study is extended, but not a
qualitative outlier in this dataset (still a strong fit). No kernel showed
a qualitatively different error pattern from the rest; MAE across kernels
(aggregated over all patches) ranges from about 0.0031 to 0.0052, and max
absolute error per kernel ranges from about 0.073 to 0.215 (all driven
primarily by the toy patch, per the scale discussion above).

## BatchNorm inspection (not folded)

`enc1.block.1` **is** a `BatchNorm2d(32)` layer immediately following the
first Conv2d (`enc1.block = Conv2d -> BatchNorm2d -> ReLU -> Conv2d ->
BatchNorm2d -> ReLU`, confirmed directly from `train_unet_baseline_tuned.py`'s
`DoubleConv` module and the checkpoint's own state-dict keys). Inspected
parameters:

| Parameter | Shape | Range |
|---|---|---|
| `gamma` (weight) | (32,) | 0.9871 to 1.0099 |
| `beta` (bias) | (32,) | -0.0059 to 0.0139 |
| `running_mean` | (32,) | -0.0152 to 0.0199 |
| `running_var` | (32,) | 0.060994 to 1.903389 |

BatchNorm folding into the Conv2d weights and bias is **mathematically
straightforward** -- a per-output-channel affine rescale:

```
w_folded[oc] = w[oc] * gamma[oc] / sqrt(running_var[oc] + eps)
b_folded[oc] = beta[oc] - gamma[oc] * running_mean[oc] / sqrt(running_var[oc] + eps)
```

**It is NOT implemented in this script.** This analysis deliberately
compares the raw Conv2d output only (no BN, no activation), matching the
exact scope of every VHDL prototype in this repo (all of which use
`bias_int32 = 0` and do not apply BatchNorm). Implementing and measuring
the effect of BN folding is a recommended next step (see below), not
completed here.

## Interpretation

- INT8 weight quantization of the real trained first-layer kernels
  introduces a small but non-zero numerical gap relative to the original
  float32 Conv2d output: **~0.8% mean relative error** (now correctly
  pooled from real-tile-dominated safe samples, not a toy-patch-only
  artifact), and correlation/cosine similarity above **0.9999** overall.
- This gap is consistent across both synthetic and real input data (drawn
  from the correct, checkpoint-matching filtered-strict split), and across
  all 32 output channels -- no channel or input type showed a qualitatively
  different quantization behavior in this sample.
- The sanity cross-check (kernel 0, top-left position, toy patch) exactly
  reproduces the VHDL-verified INT32 golden value (11287), confirming this
  script's quantization arithmetic is consistent with the already-verified
  hardware datapath before using it to measure float-vs-fixed-point
  fidelity. This was re-confirmed after both fixes in this revision.
- This is evidence that the **first-layer INT8 quantization approximation
  is numerically reasonable** for this specific layer, weight tensor, and
  quantization scheme -- but it is evidence about ONE layer's raw output
  only, not about the trained model's end-to-end segmentation behavior.

## Limitations

- **Conv-only comparison.** No BatchNorm, no activation (ReLU), no padding,
  and no downstream layers are applied -- this measures the first Conv2d's
  raw output fidelity only, not the DoubleConv block's or the model's
  output.
- **Does not claim full quantized U-Net accuracy.** No other layer in the
  network has been quantized or analyzed here.
- **Does not claim any Dice/recall/end-to-end model impact.** No
  segmentation-level evaluation (with or without quantization) was
  performed. Any statement about how this quantization error would affect
  final flood-segmentation accuracy would require a full quantized forward
  pass through the entire network and an end-to-end metric evaluation,
  which is out of scope here.
- **Small, non-exhaustive sample.** 2 real UAVSAR tiles (16x16 center crop
  each, 196 valid positions per tile) plus 1 synthetic toy patch (9 valid
  positions) -- a deliberately small, fast, "small but meaningful" sample
  per the task's instructions, not a comprehensive dataset-wide study.
- **Activation quantization scheme is new, not yet hardware-verified.**
  The per-patch symmetric activation scale used for real image data here
  has not been implemented or verified in any VHDL module in this repo --
  only the weight-quantization convention is shared with verified hardware.
- **BatchNorm not folded** (see above) -- a more realistic hardware
  approximation would need to include this.
- **No board testing, no measured power/speedup** -- consistent with every
  other document in this repo's hardware-feasibility series; this document
  makes no such claims either.

## Recommended next step

Implement BatchNorm folding (the formula above is already derived and
verified as straightforward) and re-run this same fidelity comparison with
the **folded** weights/bias against the **full** `Conv2d -> BatchNorm ->
ReLU` output (not just the raw Conv2d), to measure how much of the
remaining float-vs-fixed-point gap is attributable to the unfolded
BatchNorm/activation stage versus the INT8 weight/activation quantization
studied here. This would be the natural next increment before considering
any end-to-end quantized-model accuracy evaluation.
