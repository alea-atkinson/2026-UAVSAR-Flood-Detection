# Complete 32-Output First-Layer DSP-Aware Convolution on Artix-7 200T

Date: July 8, 2026

This document covers the complete first Conv2d layer's DSP-aware hardware
prototype and its synthesis results only. No board testing, no measured
speedup, and no measured board power are claimed anywhere in this
document.

## 1. Purpose

`enc1.block.0.weight` (the trained U-Net's first convolution tensor) has
shape `[32, 3, 3, 3]` -- 32 output channels total. Three real synthesized
DSP-aware data points already existed on the Artix-7 200T:

| Design | LUTs | Registers | DSPs | Warnings |
|---|---:|---:|---:|---|
| 8-output | 668 | 410 | 203/740 | 0 |
| 16-output | 929 | 418 | 405/740 | 0 |
| 24-output | 3374 | 706 | 731/740 | 1 (DSP overutilized; CARRY4/LUT fallback found in the final cross-channel summation stage) |

This document builds and synthesizes the **complete 32-output** DSP-aware
design -- all output channels of the first Conv2d layer -- to finish the
first-layer output-channel scaling study: does the full layer synthesize
at all on the 200T, what DSP/LUT split does Vivado choose, and is timing
still met.

## 2. Design scope

- **The complete first Conv2d layer**: all 32 output channels of
  `enc1.block.0.weight`, computed directly from real trained-model INT8
  weights. This is 32 output channels means the complete first Conv2d
  layer, **not** the complete U-Net or model pipeline.
- No BatchNorm folding, no bias beyond the (zero) Conv2d bias, no ReLU, no
  padding, no pooling, no downstream layers.
- No board testing, no measured speedup, no measured board power, no
  deployment claim.
- Synthesis target: Artix-7 200T, `xc7a200tsbg484-1`, only (35T was not
  run -- the 24-output 35T result already exceeded both LUT and DSP
  budgets, so a 32-output 35T run would only reproduce a worse version of
  that failure and was skipped per the task's guidance not to let it
  derail this task).

## 3. How the 32-output design was built from the 24-output DSP-aware design

`stream_conv3x3_3chan_32out_cell_dsp.vhd` and
`tb_stream_conv3x3_3chan_32out_cell_dsp.vhd` are **new files** -- the
existing, verified 24-, 16-, and 8-output DSP-aware designs and their
testbenches were not modified. The 32-output design is a mechanical
extension of the same structural pattern used by all prior DSP-aware
designs:

- The same 3 `window3x3_stream` instances (one per input channel), shared
  by all 32 output kernels.
- The same `conv3x3_dot_pipelined_dsp` module (DSP-steered multiplies),
  instantiated 32 x 3 = 96 times (one triplet of channel dot-products per
  kernel), vs. 72 for the 24-output design.
- The same single shared `valid_dot` gate driving all final summation
  registers, same 4-cycle latency, same 100 MHz clock target, same
  zero-bias Conv2d datapath.
- Weight/golden-output source: **all 32 kernels of `enc1.block.0.weight`**,
  generated by re-running the existing, already-generalized
  `scripts/export_first_layer_multi_kernel_vhdl_vectors.py` script with
  argument `0-31` -- no new export script was needed.
- Kernels 0-23's INT8 weight constants in the new
  `first_layer_kernels0_to31_pkg.vhd` package were spot-checked (kernels
  0, 7, 12, 18, 23) against `first_layer_kernels0_to23_pkg.vhd` and found
  **bit-identical**.

This is not a new convolution architecture: it is the same
window-sharing / DSP-steered-multiply structure used throughout this
project's first-layer prototypes, extended to cover all 32 output
channels.

## 8. 200T synthesis results

`stream_conv3x3_3chan_32out_cell_dsp` on `xc7a200tsbg484-1`
(`synth_stream_conv3x3_3chan_32out_cell_dsp_200t.tcl`):

| Resource | Used | Available | Util% |
|---|---:|---:|---:|
| LUTs | 10,461 | 134,600 | 7.77% |
| Registers | 4,618 | 269,200 | 1.72% |
| DSP48E1 | 740 | 740 | **100.00%** |
| Block RAM tiles | 0 | 365 | 0.00% |

- WNS (setup slack): **+2.343 ns** -- the 100 MHz / 10.000 ns clock is
  still met.
- WHS (hold slack): **+0.262 ns**.
- Total on-chip power (estimate): **1.324 W** (Dynamic 1.196 W, Static
  0.128 W).
- **No utilization figure exceeds 100%.** DSP48E1 usage lands exactly at
  the device's full 740-DSP capacity (100.00%), not over it -- unlike the
  24-output design's optional 35T comparison, which exceeded 100% on both
  LUTs and DSPs.
- **`synth_design` completed successfully despite the warning below.**

**The complete 32-output first-layer design synthesizes on the Artix-7
200T and still meets timing**, at the cost of fully saturating the DSP
budget and a large increase in LUT/carry-chain fallback logic compared
with the 24-output result.

## 9. Warnings/errors

Exactly 1 warning, identical in kind to the 24-output result but larger
in magnitude:

```
WARNING: [Synth 8-3323] Resources of type DSP have been overutilized. Used = 1044, Available = 740.
Synthesis finished with 0 errors, 0 critical warnings and 1 warnings.
```

No errors. The `Used = 1044` figure is Vivado's pre-fallback DSP demand
estimate (comparable to the 266 / 529 / 788 figures already seen at 8,
16, and 24 outputs); the final, actually-mapped DSP48E1 count settled at
exactly 740 (100.00%), with the remaining demand implemented in LUT
fabric (see Section 11).

## 10. Resource comparison across 8, 16, 24, and 32-output DSP-aware 200T designs

| Design | LUTs (util%) | Regs (util%) | DSP48E1 (util%) | WNS (ns) | Total power (W) | Warnings | Requested DSPs (warning) |
|---|---|---|---|---:|---:|---|---:|
| 8-out | 668 (0.50%) | 410 (0.15%) | 203/740 (27.43%) | +3.848 | 0.373 | 0 | 266 |
| 16-out | 929 (0.69%) | 418 (0.16%) | 405/740 (54.73%) | +3.848 | 0.617 | 0 | 529 |
| 24-out | 3374 (2.51%) | 706 (0.26%) | 731/740 (98.78%) | +2.760 | 1.041 | 1 | 788 |
| **32-out** | **10,461 (7.77%)** | **4,618 (1.72%)** | **740/740 (100.00%)** | **+2.343** | **1.324** | **1** | **1044** |

The requested-DSP trend (266, 529, 788, 1044) remains close to linear
(roughly +260 per +8 output channels), and at 32 outputs it lands almost
exactly at the extrapolation from the 24-output data
(`first_layer_24out_dsp_fallback_analysis.md` Section 10 projected
~1050-1060 for 32 outputs; the actual synthesized figure is 1044).

The LUT growth is sharply super-linear relative to kernel count once the
DSP budget is exceeded: LUTs grew ~3.6x from 16 to 24 outputs (1.5x more
kernels) and a further ~3.1x from 24 to 32 outputs (1.33x more kernels).
Register count also grew far faster than kernel count once fallback
began (418 -> 706 -> 4,618), consistent with pipeline/adder registers
that would otherwise be absorbed into DSP48E1 hard-macro registers
needing separate Slice Registers once implemented in LUT/carry-chain
fabric instead.

## 11. Fallback analysis

The existing `hardware/vhdl_conv3x3/analyze_dsp_lut_fallback.tcl` script
(created for the 24-output analysis) was reused, unmodified, against the
new 32-output checkpoint, writing reports to
`hardware/vhdl_conv3x3/vivado_reports_32out_dsp_200t_fallback_analysis/`.

**Primitive counts** (whole-netlist, via `get_cells -hierarchical`, cross-checked against the utilization report):

| Primitive | 24-out | 32-out |
|---|---:|---:|
| DSP48E1 | 731 | 740 |
| CARRY4 | 456 | **2316** |
| LUT2 | 1750 | **6921** |
| LUT3 | 464 | 4069 |
| LUT4 | 140 | 1478 |
| LUT5 | 337 | 441 |
| LUT6 | 1214 | 1637 |
| LUT1 | 0 | 210 (new cell type, not seen at 24 outputs) |
| FDRE | 706 | 4618 |

**Localization -- this is a cleaner (more uniform) fallback pattern than
24 outputs:**

- At 24 outputs, 22 of 24 kernels' final cross-channel summation
  (`y{k}_r <= bias + y_c0 + y_c1 + y_c2`) still got a dedicated top-level
  DSP48E1, with only kernels 7 and 18 losing DSP mapping entirely, and
  most others showing a hybrid CARRY4+DSP48E1 split.
- At **32 outputs, zero of the 32 kernels' final-sum registers appear as
  a top-level DSP48E1 cell.** `get_cells -hierarchical -filter {REF_NAME
  == DSP48E1}` returns no top-level (non-`dot_k*`-prefixed) matches at
  all; every one of the 740 DSP48E1 cells is nested under a `dot_k{k}_c{ch}`
  instance. Cross-checking the CARRY4 list shows **all 32** kernels'
  `y{k}_r_reg` names present there instead.
- `report_utilization -hierarchical -hierarchical_depth 4` corroborates
  this at the top level: the top-level `(stream_conv3x3_3chan_32out_cell_dsp)`
  row shows **0 DSP Blocks** locally (vs. 22 at 24 outputs, 16 at
  16 outputs, 8 at 8 outputs), and **all 96** `dot_k{k}_c{ch}` sub-instances
  now show non-zero local LUTs and 32-35 FFs each -- compared with only
  16 of 72 such instances at 24 outputs. This means essentially none of
  the per-channel dot-product instances' internal pipeline registers were
  absorbed into DSP48E1 hard-macro registers this time; all 96 retained
  some local flip-flop content.
- **Interpretation, stated carefully:** the evidence is consistent with
  all 740 available DSP48E1 resources being fully consumed by the 96
  per-tap multiply-accumulate datapaths (6-9 DSPs per instance, similar
  to the 7-11 range seen at 24 outputs), leaving **zero DSP48E1 capacity
  for any kernel's final cross-channel summation stage**, which is why
  the fallback at 32 outputs is complete and uniform across all 32
  kernels rather than partial/hybrid as it was at 24 outputs. This is
  inferred from cell counts and hierarchical naming, not from a
  cycle-by-cycle trace of Vivado's internal resource-allocation
  algorithm.
- As at 24 outputs, this analysis does **not** claim to know exactly
  which individual per-tap multiplies (inside the 96
  `conv3x3_dot_pipelined_dsp` instances) mapped to LUT fabric versus
  DSP48E1; the 6-9 DSP48E1 count per instance (out of 9 raw taps) is
  reported as-is without a per-tap causal explanation.

## 12. Interpretation for complete first-layer feasibility

- **This implements the complete 32-output first Conv2d layer.**
- **The design passes GHDL with 288 checks** (9 positions x 32 kernels).
- **The design synthesizes on Artix-7 200T**, meeting timing at +2.343 ns,
  with DSP48E1 usage landing at exactly 100.00% (740/740) and 1
  DSP-overutilization warning during synthesis (`Used = 1044, Available =
  740`).
- **The 32-output result completes the first-layer output-channel scaling
  study**: on this specific larger target, direct fully parallel
  DSP-aware mapping of the complete first Conv2d layer is
  synthesizable and timing-closes at the `synth_design` (out-of-context)
  level, but only by fully consuming the device's DSP budget and pushing
  the entire final cross-channel summation stage, for all 32 kernels,
  into LUT/carry-chain fabric -- a substantially larger and more uniform
  fallback than was seen at 24 outputs.
- **This indicates that direct, fully parallel first-layer DSP-aware
  mapping is synthesis-feasible on the Artix-7 200T for the complete
  32-channel layer**, but the resulting design is DSP-saturated (0 DSPs
  of headroom remain) and relies on a substantial, now fully uniform,
  LUT+CARRY4 fallback for the cross-channel summation stage. It is not a
  clean, comfortably-margined result the way the 8- and 16-output designs
  were.

## 13. Limitations

- First-layer convolution only: this implements the complete first
  Conv2d layer's output channels, **not** the complete U-Net and **not**
  end-to-end flood segmentation.
- No BatchNorm, folded bias, ReLU, padding, or pooling in this VHDL.
- No board testing, no measured speedup, no measured board power --
  all figures are Vivado `synth_design` / `report_timing_summary` /
  `report_power` (vector-less, "Medium confidence") estimates, not
  measurements from a running device.
- This is a synthesis-level (out-of-context `synth_design`) result, not
  placed-and-routed or implemented; a DSP utilization of exactly 100%
  leaves no margin, and place-and-route could behave differently from
  this synthesis-level estimate.
- Fallback localization (Section 11) is based on cell-naming and
  hierarchical-utilization evidence, not a full per-multiplier trace;
  the per-tap DSP48E1 count variation (6-9 per instance) is reported
  without a proven causal explanation.
- No 35T synthesis was attempted for the 32-output design (skipped
  per task guidance, given the 24-output 35T result already exceeded
  both LUT and DSP budgets).
- This does not prove the complete U-Net fits, does not prove
  end-to-end flood segmentation runs on FPGA, is not board-tested, and
  does not prove measured speedup, measured power, or deployment
  readiness.

## Recommended next step

Since the complete 32-output first-layer design is now DSP-saturated
(100.00%, 0 headroom) with a fully uniform LUT/CARRY4 fallback for the
final summation stage, the most informative next step is **not** further
output-channel scaling (32 is already the complete layer) but moving to
the next stage of the FPGA feasibility question: evaluate whether this
32-output design's resource footprint (10,461 LUTs, 4,618 registers, 740
DSPs, 0 BRAM) leaves enough headroom on the 200T to also host the next
model stage (e.g., BatchNorm folding and ReLU for this same layer, which
would add elementwise arithmetic but no new multiplies), as a synthesis
experiment -- rather than attempting a larger or different first-layer
variant, since the output-channel scaling story for this layer is now
complete.
