## Analysis

### 1. Does batching improve GPU throughput?

**Yes.** bs=8 achieves 117.6 tiles/sec vs 93.5 at bs=1 (1.3× speedup). GPU parallelism is underutilized at single-tile inference.

### 2. Does num_workers reduce data loading bottleneck?

**Yes.** nw=4 reduces pipeline time by 79% (8.93 → 1.91 ms/tile). Background workers overlap I/O with the prior batch's GPU compute.

### 3. How fast is model-only inference when tensors are already loaded?

**1.18 ms/tile** at bs=1 (802.9 tps). Best at bs=4: 0.94 ms/tile (1017.7 tps). This is the theoretical minimum — no rasterio, no normalization, tensors already in CPU RAM.

### 4. Is raster loading/preprocessing the real bottleneck?

**Yes — raster I/O dominates.** Loading + normalize = 8.04 ms/tile (87% of I/O+forward). Model forward = 1.18 ms/tile. Pre-normalizing tiles offline would nearly double pipeline throughput.

### 5. What does this imply for FPGA acceleration?

The host CPU spends more time on rasterio/normalization than the model spends on compute. An FPGA accelerator gains the most by **eliminating host-CPU I/O** — either pre-process tiles to normalized float32 tensors offline, or implement lightweight normalization on the FPGA front-end. The Conv2d pipeline itself is fast; the bottleneck to remove first is the disk→CPU→normalize path.

### 6. What should the next hardware step be?

1. **Pre-normalize tiles offline** — save as `.npy` or `.pt` tensors, eliminating rasterio + percentile normalization at inference.
2. **Increase batch size** to bs=8 for best GPU throughput.
3. **Export to ONNX** → benchmark with TensorRT for production GPU deployment.
4. **FPGA path**: ONNX → INT8 quantization → Vitis-AI synthesis (Zynq UltraScale+).
